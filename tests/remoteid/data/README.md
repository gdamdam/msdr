# Remote ID test vectors

`vectors.json` is generated by `tests/remoteid/gen_vectors.c`, which links
against `opendroneid-core-c` (Apache-2.0,
https://github.com/opendroneid/opendroneid-core-c) at commit
`6484f26545d4f012682524e2d843fab0fbdc0b34`: `libopendroneid/opendroneid.c`,
`libopendroneid/opendroneid.h`, `libopendroneid/wifi.c` and
`libopendroneid/odid_wifi.h` (not vendored into msdr; see
`msdr/remoteid/` module docstrings and `THIRD_PARTY_NOTICES.md`).

Each vector gives the hex bytes of an encoded message (or message pack, or
full Wi-Fi Beacon frame) alongside the decoded field values opendroneid-core-c
itself produced for them -- an independent cross-check of
`msdr/remoteid/messages.py`, which was written by hand from the same C
source rather than transliterated from it. Message/field values for
`basic_id_serial`, `location_normal`, `auth_page0`, `auth_page1`, `self_id`,
`operator_id` and `message_pack_7` mirror `test/test_inout.c`'s own example
drone. `location_unknown`/`system_unknown` exercise every "no value" sentinel
(`odid_init*Data()` defaults); `location_boundary` exercises the maximum
representable lat/lon/altitude/speed and the direction/timestamp wrap at
360 deg / the top of the hour; `basic_id_utm_uuid` exercises a binary
(non-string) UASID.

## Regeneration

Requires a C compiler (`cc`) and opendroneid-core-c's sources renamed to
their upstream basenames (`opendroneid.c`, `opendroneid.h`, `wifi.c`,
`odid_wifi.h`) in one directory, because `wifi.c` assumes glibc's
`<byteswap.h>`, which macOS lacks; `gen_vectors.c`'s header comment gives a
small shim (`bswap_16/32/64` via `__builtin_bswap*`) to put in a second `-I`
directory on macOS.

```sh
cc -I<odid_dir> -I<shim_dir> -o /tmp/gen_vectors \
   tests/remoteid/gen_vectors.c <odid_dir>/opendroneid.c <odid_dir>/wifi.c -lm
/tmp/gen_vectors > tests/remoteid/data/vectors.json
```

This was run locally (macOS, Apple clang) to produce the committed
`vectors.json`; no off-air capture is involved.
